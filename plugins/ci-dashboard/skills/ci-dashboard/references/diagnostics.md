# CI diagnostics and elapsed timings

Read when you interpret CI health problems and alerts, the shared Workflow and Event choice, or timing diagnostics.

CI health lists *problems*: open critical or warning job-level signals and run-level alerts. Run-level alerts flag the latest non-cancelled/non-skipped failed run per workflow on the actual default branch and three or more consecutive failures on any branch (workflow and branch kept separate; PR runs never become default-branch alerts; a later success clears the alert; neutral/unknown results break a streak; failure states are failure, timed_out, startup_failure, action_required and stale). Each problem can be **dismissed** (moves under a collapsed Dismissed section, restorable) or handed to a BB session with **Investigate** (a new session in the BB project linked to the repository, or an existing session picked from that project; busy sessions queue the message). Investigating problems show a link to the session. Handled problems stop counting in the navigation badge. Failures on steps listed in the `refusalSteps` setting (comma-separated; blank by default) are classified `refused` (an intentional gate refusal, e.g. a stale candidate): not real, not a runner loss, no job signal, and a run-level alert is dropped when its latest attempt has only refused, aggregator or cancelled jobs. The `flakeSignatures` setting (one `<regex> => <label>` per line, blank by default) turns a failed job that would be `real` into a `flake` when its annotations, full log or an artifact named by `flakeArtifacts` (comma-separated globs, blank = never download) match a rule; the label shows as evidence, and changing the rules re-scans stored jobs within the job-backfill budget. The Investigate prompt starts with a Verdict (per-class counts of the problem's non-success jobs and a yes/no/unknown "Code looks broken"), then covers the problem's runs (streak start, commit and PR title), newer runs and whether each failed job has since passed, the latest deployment per environment, per-day rates over the stored window, and a suggested action per class with who acts; the free-text `investigateNotes` setting (blank by default) is appended verbatim under Team notes for a team's own rerun limits or incident links. It is built from memory and the local store only. Everything else (outcome counts, failure causes, main/PR success rates that exclude cancelled and skipped runs, runner pools, losses, reruns, resolved incidents, history coverage notes, top failing workflows, the lazy failed-run list) is in one collapsed Details.

The timing summary and both history charts share one Workflow and Event choice per repository (stored in the browser, so switching repository tabs restores each one's choice). It defaults to the main pipeline (the workflow with the most successful run time) and, when that workflow has several events, its busiest event; All workflows and All events pool. Changing it recalculates nothing remotely: it uses the cached per-workflow aggregates. Median, average, P95, total and coverage all follow this selector; the workflow breakdown and longest-run list remain repository-wide. All workflows is a pooled run distribution, not a typical CI duration: frequent short automation can dominate its median. CI run timings prioritizes median, mean and nearest-rank P95 as the three large statistics, with total estimated elapsed time in a secondary text line. The P95 label explains on hover that approximately 95% of measured successful runs finish at or below this duration. The card also shows expandable timing statistics per workflow, and the five longest successful runs with GitHub links. Estimates use run_started_at through updated_at for the current completed run record. Missing or invalid intervals are omitted and measured/total coverage is displayed. Only successful completed runs contribute to all timing statistics and the longest-run list. Cancelled, skipped, failed, timed-out, neutral and unknown conclusions are excluded; counts show measured versus successful runs plus the number excluded. Summed elapsed durations include overlapping workflows; they are not wall-clock delivery time, job compute time or billed runner minutes. Reruns or later record updates may inflate estimates; individual attempt history is not fetched.

Runs of one workflow are never silently mixed across events: a workflow may run a light preflight on `pull_request`, the full check on `merge_group` and something short on `push`, and pooling them would make a daily median move with the day's event mix. When the selected workflow has two or more events, the timing summary gets an Event selector (default: the main event, the slowest per successful run among events with at least a tenth of the workflow's successful runs, i.e. the full check; or All events), and the workflow breakdown lists each event's median and sample size. The Median CI run duration and CI run duration p90 charts get the same Event selector and default to the main event, with the shown event in the note under the title; run-count charts default to All events. Each bar of a sample-based chart shows `n <samples>` under its value, and its tooltip says what the value is a median or p90 of (failed, cancelled and skipped runs are excluded). The agent summary carries the same split as `ciInsights.workflows[].events` (`event`, `total`, `passed`, `timing`).

Diagnostics use metadata already returned by workflow-list requests and derive locally from the same retained raw history on date changes. No per-run or per-job timing requests are added. Existing cached histories remain readable; a refresh acquires missing metadata, with versioned HTTP cache keys preventing legacy slim responses from being retained by a 304. Partial CI histories never produce diagnostics or timing totals.
