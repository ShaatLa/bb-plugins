# Observer event lines

Read when you handle observer event lines: event types, noise control, latency and deployment lines.

What is sent (each type has its own on/off setting, all on by default):

- Merge queue removal (`observeQueueRemoval`): `PR #N removed from merge queue · <job>: <class>[ <signature label>], … · failed tests: <up to 3, then +K> · inspect queue:<run>:<attempt>` + run link. Classes are the classifier's (`real`, `flake` with the known-flake label, `runner_loss`, `consequence`, …). A group builds on the group ahead: when that group failed the same job with the same build failure (or known-flake label, or failed tests), the job reads `… inherited from #A` and, if every own failure is inherited, the line starts `PR #N removed (inherited from #A)`; `ref=job:…`/`ref=queue:…` show `inheritedFrom` and relate `pr:A` and `run:<A's run>`. Failed test names exist only when `flakeArtifacts` names a test-report artifact (Go test2json, Jest/Vitest JSON, JUnit XML) and come from FAILED entries only. When a job failed `real`, the line is followed by `  - <test>: <message>` per shown test: the first failure message of a failed test (its assertion or error lines up to the stack, at most 200 characters, with env assignments, tokens, credentials and home paths redacted).
- Removals are confirmed against the PR's merge-queue timeline (GitHub `REMOVED_FROM_MERGE_QUEUE_EVENT` after the group started, retried for 15 minutes, a failed lookup falls back to sending), and only groups with an own failure that the queue did not invalidate by cancelling or replacing them are announced.
- Runner loss on a merge queue or default-branch push run (`observeRunnerLoss`): `Runner lost · <job> · runner <name> · <N>[/limit] losses on head <sha7>[ · problem <id>] · inspect job:<id>` + job link. The limit appears when `runnerLossLimit` is above 0. A merge queue loss is not a separate line: it is folded into the removal as `<job>: runner_loss (<N>[/limit] on this head)`, and appears as this line only when the PR stayed in the queue (its removal was never confirmed within 15 minutes); default-branch push losses always use this line.
- Default-branch workflow red (`observeDefaultRed`): `<workflow> red on <branch> · jobs: <class counts> · Code looks broken: yes | no | no (red on flakes only) | unknown (deploy path failed) | unknown[ · problem <id>] · inspect run:<id>:<attempt>` + run link. The verdict is the one Investigate prompts use.
- Pool stall (`observePoolStall`, threshold `stallMinutes`), mass cancel (`observeMassCancel`), deployment finished (`observeDeployments`: `Deploy <environment> <success|failure|error> · <sha7> · deployment <id>` + log link).

Every line except deployments ends with `inspect <ref>` before the link (`queue:`, `job:`, `run:` or `pool:` refs; stalls and mass cancels also keep ` · problem <id>`): pass it to `ci_dashboard_metrics` as `ref` for the facts the line leaves out. Never included: log text, annotations, signature match text, env values (except the redacted first failure message of a `real` test failure, above). Only labels, ids, names and links.

Noise control: every event has a key (`queue:<run>:<attempt>`, `loss:<jobId>`, `red:<run>:<attempt>`, the signal id for stalls and mass cancels, `deploy:<id>:<state>`). Sent keys are persisted in plugin kv (`observer:<repo>`) and kept for the job-history window plus a day, so a restart or reload never repeats an event. A key that can reopen (a pool stall) is repeated only after `observerQuietMinutes` (default 30; 0 repeats at once). `observerBatchMinutes` above 0 collects events into one digest, one line each, sent once the oldest has waited that long. For observer subscriptions, nothing before a subscription is replayed: a thread only receives events that happened after it subscribed, and an event type switched on later (or off and on again) starts from that moment.

Latency: the live poll (every 60 s) notices a run that is no longer queued or in progress, fetches it (1 request) and, if it ended unsuccessfully, stores its jobs ahead of the history backlog and re-runs the analysis in the same loop, so a queue removal or runner loss reaches the observer within about a minute of the job's completion. A run that starts and ends between two polls is picked up by the periodic history refresh instead.
PR subscriptions were removed in 0.8.0.

Deployment lines name the PR when known. `observeDeployments` accepts `all` (default), `failures` (failure, error and gate refusal), or `off`; old boolean settings still work. A gate refusal is superseded, and sent to nobody, when a newer deployment of another commit to the same environment is running or succeeded; with no newer deployment yet it waits up to 10 minutes, then reports as a refusal.
