# CI Dashboard

Open **CI Dashboard** in the navigation sidebar (pipeline icon), route `/plugins/delivery-dashboard/dashboard`. It no longer appears on New thread.

Configure in Settings → Plugins → CI Dashboard:
- `repository`: additional GitHub `owner/repo` entries, comma-, whitespace-, or newline-separated. Existing single entries remain valid.
- `importBbRepositories`: enabled by default. Imports GitHub `gitRemoteUrl` values from all BB projects on each refresh, skipping non-GitHub hosts and missing remotes. SSH/SCP, HTTPS, and Git formats work. Entries are de-duplicated case-insensitively. Disable to use only the manual list.
- `token`: optional secret override. Blank uses `GH_TOKEN`, then `GITHUB_TOKEN`, then the active GitHub.com account from `gh auth token --hostname github.com` on the BB server machine. Never print credentials or pass them in chat. The token is not copied to settings or sent to the frontend. Without credentials, public-repo access is anonymous.
- `refreshSeconds`: integer 30–3600; default 300. Applies without reload.

The sidebar page shows a separate section per repository, with deployment records per day averaged over the selected range (all environments/outcomes), current open PRs including drafts, and successful / completed GitHub Actions workflow runs excluding cancelled and skipped created within the selected range. Cancelled and skipped runs are excluded from the CI pass-rate denominator and chart, but kept in the CI outcomes breakdown. Neutral and failed completed runs count in the denominator. A history containing only cancelled/skipped runs has an empty rate.

Frontend polling runs while the dashboard page is mounted, after each request settles. The Refresh button retries immediately. Failed metrics show an error rather than zero. A failed RPC retains values marked stale. The backend aborts requests on unload and bounds each API request to 20 seconds. Deployments are paginated until the selected window is complete; repeated or empty intermediate pages fail explicitly.

For private repositories use a fine-grained token scoped to the repository with Actions, Deployments, Pull requests, and Contents read permissions (plus GitHub's required metadata access); organization SSO may require authorization. GitHub.com only. Data comes from GitHub REST APIs on the BB server. The token is never returned to the browser.

BB project discovery failures appear in the UI while manual repositories still load. Projects without a recorded remote need a manual entry. The same repository list appears on the dashboard page.

No custom CLI is needed: native ci_dashboard_metrics and the discoverable read-only ci RPC provide agent access. Use `bb plugin config delivery-dashboard` for non-secret settings, and the settings UI for credentials. Build with `bb plugin build <plugin-path>` before install or release.

The 1-day preset means today from 00:00 UTC through refresh time for all historical cards. Its charts show six four-hour intervals starting at 00:00, 04:00, 08:00, 12:00, 16:00 and 20:00 UTC. Future intervals show “—” and are disabled; the current interval ends at refresh time. Today’s deployment frequency is the count since midnight. Custom single-day charts keep hourly buckets. The rolling three-day preset uses six 12-hour buckets. Other charts show daily buckets up to two weeks, and at most 14 larger whole-day buckets for longer ranges, with UTC labels. The final bucket may be shorter; hover details show its actual boundaries. Deployment counts and CI success percentages come from GitHub records. CI days without runs show “—”. Large CI histories are split into disjoint UTC time searches of at most 1,000 runs each. Failed pagination or inconsistent counts are unavailable; capped large-search counts never produce a precise summary.

Additional sections per repository:
- CI outcomes count each conclusion in the same complete selected-range run dataset as the pass rate and chart. Failed, cancelled, skipped, timed out, etc. are separate. Large histories split automatically; incomplete/changing pagination hides the breakdown and series. A fallback summary is used only for searches of at most 1,000 runs. Complete histories no longer depend on a separate success-count query.
- PRs awaiting review use `is:pr is:open draft:false review:none`, show the five oldest and total, and link to GitHub. Age is since opening, not time waiting for a review request.
- Latest production deployment is independent of the selected window: scan deployments newest first until production is found or the list ends for `production_environment: true` or an environment named `production` case-insensitively. Latest status, environment/ref, creation age, update time, and a safe HTTPS log link are shown. Missing status is unknown; unsafe/missing log URLs fall back to GitHub's deployment list. Repeated or empty intermediate deployment pages are an error.

Repository activity shows PRs created over the same selected range (all states, including drafts), plus default-branch commits and cumulative additions/deletions. Commit history is filtered by committed date. Sums cover all file types and merge commits as GitHub reports them; they are not net growth or source-code-only LOC. GraphQL is used for commit statistics, requiring a system/override token even for public repositories. Pagination is anchored to the initial head commit, de-duplicated and checked for completeness without a 1,000-commit cap. Incomplete results show unavailable values, not partial totals; empty repositories/history show real zeroes. The displayed branch identifies the commit scope; PR counts are repository-wide.

Refreshes are silent once data is available: existing cards/charts remain visible and the Refresh button keeps a stable width. Sidebar remounts reuse the current window snapshot; new windows read the persisted server snapshot before collecting fresh GitHub data in the background. Browser storage is not used. The last-checked time identifies the displayed snapshot, and failed RPC refreshes retain values with a stale-data warning.

Use the Date range selector for today (1 day), or 3, 7 (default), 14, 30, or 90 rolling days. Custom dates uses From/Through date inputs and Apply dates, includes both dates in UTC, caps today at refresh time, and rejects invalid/reversed/future dates and dates before the UTC calendar date one year ago (February 29 maps to February 28 in a non-leap year). Filters apply to deployment frequency, created PRs, commit/line activity, CI summary/outcomes, and charts for every repository; open PRs, review queue, and latest production remain current state. Previous results keep their own loaded range captions during a filter change. Superseded responses cannot replace newer selections. The filter selection survives sidebar remounts within the current window. RPC metrics accepts null (default week), { days: 1|3|7|14|30|90 }, or { start: "YYYY-MM-DD", end: "YYYY-MM-DD" }.

Click a bar in either history chart, including empty elapsed bars, to open Interval statistics for that repository and exact UTC bucket boundaries. Keyboard Enter/Space also opens it. The popup loads on demand and shows deployments, created PRs, commits, lines added/deleted, CI pass rate, and CI outcomes. Buckets can be hourly, rolling daily, or multiple days; do not describe a multi-day bucket as a calendar day. Earlier buckets exclude the shared endpoint, avoiding double counting. Close/Escape/backdrop dismiss the modal; failed requests offer Retry, and the underlying dashboard remains visible and keeps its filter. The interval RPC accepts { repository, since, until } with validated ISO UTC endpoints within the past year through now.

Repository headings use the first matching BB project name, capitalized, falling back to the repository name with hyphens/underscores replaced by spaces. The owner/repository identifier remains in the heading tooltip. Period captions start with a capital letter and use compact UTC calendar dates; exact UTC endpoints are in the tooltip. The unlabeled, accessible date selector and Refresh button sit next to each other, with custom date inputs below. Refresh is a borderless square icon button with the accessible name Refresh. The single clockwise reload arrow spins clockwise during loading, keeps its size and respects reduced-motion preferences. Repository headings and external navigation links use compact ExternalLink icons. Previous results remain visible without a date-range update message.

The interval popup is centered and constrained within the dashboard pane intersected with the visual viewport, with 16px outer margins. A ResizeObserver tracks pane/split resizing so an adjacent native browser cannot cover it; visual viewport listeners also handle pinch zoom, panning, and on-screen keyboard changes. Its cards adapt to the available width and overflow scrolls vertically. The pane observer and viewport listeners are removed on close.

CI history first determines whether a search needs splitting, then fetches each leaf search’s remaining pages concurrently (at most nine more). A shared four-request budget covers all repositories, interval requests and background refreshes. Per-request deadlines start after queueing. Counts, unique run IDs, UTC boundaries and final pagination markers are checked before showing complete history.

Opening the dashboard reads a persisted server snapshot before refreshing from GitHub. A background service keeps the default weekly range warm while the page is closed, using refreshSeconds. Eight recently requested ranges survive plugin/BB restarts in plugin-owned SQLite; settings changes clear them and invalidate older in-flight writes. Concurrent refreshes of a range are coalesced. Snapshots contain no credentials. The 600 ms display budget targets existing snapshots; a first-ever or uncached range still needs GitHub collection. Last checked identifies the snapshot time, and failed background requests preserve displayed values with a warning. Browser storage is not used.


The latest-production-deployment card of the configured repository includes **Deploy to production**. The action is configurable and hidden until set: `productionRepository` (owner/repo, blank = disabled), `productionWorkflow` (workflow file name, required with a repository) and `productionRef` (branch or tag, default `main`). Confirming starts that workflow on that ref, preserving the workflow's own checks and GitHub approvals. The target comes only from settings; arbitrary repositories, refs, and workflow paths cannot be supplied. The backend refuses unless both repository and workflow are set and the repository is still one of the configured/imported dashboard repositories, and it blocks overlapping dispatch requests. The existing GitHub authorization must have [Actions write permission](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event). Success means the workflow was requested, not that production has deployed; use View workflow to follow it. Requests are never retried automatically; after an unconfirmed request, check GitHub before trying again.

Repository headings link directly to their GitHub repository using BB’s standard URL opener (the right Browser pane when the built-in browser is selected). Normal link modifiers and copy-link behavior remain available. The dashboard uses a pipeline icon in the sidebar and plugin branding.

The window retains eight range snapshots keyed by configuration and selection. Returning to a loaded range renders its cards immediately while metrics refresh in the background. Completed superseded requests still populate their own cache entry, without replacing the current view; settings changes invalidate pending cache writes. Persisted snapshots only seed ranges absent from memory, so polling cannot reapply older server data.

Complete deployment, CI and commit records are stored with their source snapshot in plugin-owned SQLite. An uncached preset or custom range contained in a stored history is computed locally, anchored to the source snapshot’s endpoint and last-checked time. The local snapshot returns immediately with the created-PR count marked pending; the regular metrics request fills that count separately. Current open PRs, reviews and production reuse the source snapshot. Ranges outside stored coverage require a first GitHub collection; existing aggregate-only snapshots need one refresh to acquire raw history.

Fresh range snapshots are reused until refreshSeconds expires; changing dates does not start another full collection while the cached data is fresh. The Refresh button explicitly forces collection, and expired data refreshes in the background.


Side cards use their content height. Expand **Latest failed runs** in CI health for up to five workflow runs with the failure conclusion, created in the displayed range, with workflow/title, creation time and GitHub run links. Expand **Recent production deployments** for the five latest deployments in the latest production deployment’s environment, with status, ref, SHA and creation time. Compare links use adjacent immutable deployment SHAs and are omitted for identical SHAs. A failed status lookup is shown as unavailable. These lists load only on expansion, share the four-request GitHub budget and 20-second timeout, and keep their response while that snapshot is displayed; closing/reopening does not fetch again. A changed range or refreshed snapshot resets the lists. Errors offer Retry details. Production history is independent of the selected historical range. Refresh uses an inline SVG reload icon so its shape does not depend on the host icon-name mapping.


Repository history is shared across date selections in SQLite, independently of the eight rendered range snapshots. Overlapping requests extend the stored coverage; routine refreshes retain at most the rolling 90-day span unless an explicitly requested custom range needs older data. Repository history refreshes are coalesced across selections. A fresh contained view reuses that history and only obtains its range-specific PR creation count. Snapshot derivation is fully local and never resolves GitHub authorization or waits for a PR API request; unavailable creation counts are marked pending, not zero. Historical dates remain anchored to the source endpoint and timestamp.

Refreshes publish ready repository cards on the metrics-progress channel before the full request settles. The page accepts only its selected range, rejects older request generations, and displays pending fields explicitly. A slow commit history or another repository does not delay ready CI, deployments, PRs or reviews. A failed refresh still preserves the available view.

A shared persistent response cache revalidates GET pages with ETag/If-None-Match, retaining the body and pagination on 304; unsupported endpoints fall back to normal GET. Metadata (PR counts, review queue and deployment statuses) has a separate refreshSeconds lifetime shared across date selections. Manual Refresh bypasses that lifetime and revalidates. Cache keys contain a token hash, never the token, and settings changes clear both histories and HTTP responses and reject old in-flight writes. Up to 512 HTTP pages are retained; cached payloads store only the fields used by metrics, excluding unused deployment payloads and unsafe log links.

Large CI collections use stable UTC week windows, running independent windows and the first split’s siblings concurrently. Deeper splits are sequential to prevent exponential speculative work when GitHub reports inconsistent counts. The active tail is read after closed windows so its pages do not queue behind historical work; a pagination count change retries only that window once before reporting incomplete data. All paths retain the shared four-request limit, per-request deadline, complete leaf count checks, duplicate-ID checks and disjoint boundaries. Old CI pages are revalidated too, so reruns that change an old conclusion are not silently frozen in cache. Unchanged pages need no response-body download.

Commit history always checks the current default-branch head and total count. An unchanged head reuses complete matching cached records. A fast-forward can merge new records only after encountering the prior head (proving ancestry) and matching the complete expected count. A rewritten branch, changed branch, missing ancestry or incomplete merged count falls back to reading the current immutable-head history. First loads, missing coverage, missing ETags and rewritten Git history can still require full downloads.


Automatic cache maintenance runs at startup, after completed snapshot writes and successful repository discovery, and hourly through the existing background service. Entries unused for seven days are removed. Historical records are limited to the past calendar year, from 00:00 UTC on the anniversary date through now. Older raw deployment, CI and commit records are pruned while newer records and their actual freshness timestamps survive. Snapshots with older aggregate windows and HTTP pages containing older history or querying older date ranges are removed whole, preserving pagination counts and ETag correctness. Current-state metadata such as old pull requests still open is retained. The boundary advances daily; cleanup runs at startup and at least hourly while idle. Last access is tracked separately from the data’s freshness timestamp, so using a cached entry never makes old metrics appear freshly collected. Existing repository histories receive an initial access timestamp on upgrade; existing HTTP pages inherit their previous check time. Valid local snapshot reads keep the corresponding repository history active.

Cache budgets retain at most eight range snapshots and 512 HTTP responses, with a combined 64 MiB budget for serialized cache payloads (SQLite/WAL overhead is additional). Byte eviction removes least-recently-used HTTP pages first, then range snapshots, then repository histories, retaining active history ahead of disposable responses. An entry larger than the whole budget may be evicted; subsequent requests collect it again normally, without treating missing history as zero. Successful, complete project discovery removes histories, snapshots and recognized HTTP pages belonging to repositories no longer configured. Discovery failures do not purge unknown repository membership.

SQLite compaction runs only at startup or the hourly idle maintenance pass, with no metrics/history request in flight: VACUUM is used when free pages occupy at least 8 MiB and 25% of the file; WAL is checkpointed and truncated. Normal request completion only evicts rows. Maintenance failures are logged and retried later without failing metric requests. Cache deletion never modifies repositories or GitHub data.


### CI diagnostics and elapsed timings

CI health lists *problems*: open critical or warning job-level signals and run-level alerts. Run-level alerts flag the latest non-cancelled/non-skipped failed run per workflow on the actual default branch and three or more consecutive failures on any branch (workflow and branch kept separate; PR runs never become default-branch alerts; a later success clears the alert; neutral/unknown results break a streak; failure states are failure, timed_out, startup_failure, action_required and stale). Each problem can be **dismissed** (moves under a collapsed Dismissed section, restorable) or handed to a BB session with **Investigate** (a new session in the BB project linked to the repository, or an existing session picked from that project; busy sessions queue the message). Investigating problems show a link to the session. Handled problems stop counting in the navigation badge. Failures on steps listed in the `refusalSteps` setting (comma-separated; blank by default) are classified `refused` (an intentional gate refusal, e.g. a stale candidate): not real, not a runner loss, no job signal, and a run-level alert is dropped when its latest attempt has only refused, aggregator or cancelled jobs. The `flakeSignatures` setting (one `<regex> => <label>` per line, blank by default) turns a failed job that would be `real` into a `flake` when its annotations, full log or an artifact named by `flakeArtifacts` (comma-separated globs, blank = never download) match a rule; the label shows as evidence, and changing the rules re-scans stored jobs within the job-backfill budget. The Investigate prompt starts with a Verdict (per-class counts of the problem's non-success jobs and a yes/no/unknown "Code looks broken"), then covers the problem's runs (streak start, commit and PR title), newer runs and whether each failed job has since passed, the latest deployment per environment, per-day rates over the stored window, and a suggested action per class with who acts; the free-text `investigateNotes` setting (blank by default) is appended verbatim under Team notes for a team's own rerun limits or incident links. It is built from memory and the local store only. Everything else (outcome counts, failure causes, main/PR success rates that exclude cancelled and skipped runs, runner pools, losses, reruns, resolved incidents, history coverage notes, top failing workflows, the lazy failed-run list) is in one collapsed Details.

The timing summary has a workflow selector: it defaults to the workflow named CI (case-insensitive), or All workflows if absent. Changing it recalculates nothing remotely: it uses the cached per-workflow aggregates. Median, average, P95, total and coverage all follow this selector; the workflow breakdown and longest-run list remain repository-wide. All workflows is a pooled run distribution, not a typical CI duration: frequent short automation can dominate its median. CI run timings prioritizes median, mean and nearest-rank P95 as the three large statistics, with total estimated elapsed time in a secondary text line. The P95 label explains on hover that approximately 95% of measured successful runs finish at or below this duration. The card also shows expandable timing statistics per workflow, and the five longest successful runs with GitHub links. Estimates use run_started_at through updated_at for the current completed run record. Missing or invalid intervals are omitted and measured/total coverage is displayed. Only successful completed runs contribute to all timing statistics and the longest-run list. Cancelled, skipped, failed, timed-out, neutral and unknown conclusions are excluded; counts show measured versus successful runs plus the number excluded. Summed elapsed durations include overlapping workflows; they are not wall-clock delivery time, job compute time or billed runner minutes. Reruns or later record updates may inflate estimates; individual attempt history is not fetched.

Diagnostics use metadata already returned by workflow-list requests and derive locally from the same retained raw history on date changes. No per-run or per-job timing requests are added. Existing cached histories remain readable; a refresh acquires missing metadata, with versioned HTTP cache keys preventing legacy slim responses from being retained by a 304. Partial CI histories never produce diagnostics or timing totals.


Dashboard hierarchy: headline success/deployment/PR metrics first, then a full-width CI run timings card with larger timing values and side-by-side expandable workflow/run lists, followed by a unified CI health card. CI health shows the problem list first and one collapsed Details with the rest. CI and deployment history charts follow, then repository activity, then equal-width review and production cards. Secondary cards retain content height; all multi-column layouts stack on narrow screens. Interval dialogs keep the compact CI outcomes card without the dashboard-only diagnostics.


Loading states use theme-aware neutral skeletons shaped like KPI values, timing statistics, CI signals/outcomes, activity numbers, lists and charts. The initial dashboard also shows a structural skeleton; lazy details and interval dialogs follow the same pattern. Each pending field reveals independently. Available values stay visible even when marked pending, zeroes remain values, and failures/unavailable data retain explanatory messages rather than skeletons. Skeletons are decorative, with a named busy status for assistive technology, and disable pulsing when reduced motion is requested.


Expanded timing lists use compact inset rows with aligned duration values. Workflows sort by average duration descending (missing averages last); average is the prominent value, with median, P95, measured-run coverage and cumulative total in secondary metadata. Longest-run links separate workflow, duration, branch and run ID; long branch names truncate visually with their full name in the tooltip and accessible link label.


## Agent access

Use the native **ci_dashboard_metrics** tool to read CI data. For example:

```json
{"repository":"owner/repo","selection":{"days":7},"refresh":false}
```

Omit repository for all configured dashboard repositories. Selection defaults to seven days and accepts the same presets or inclusive UTC custom dates as the UI, limited to the past year. Cached local snapshots are returned immediately when available, even if stale; inspect source, updatedAt, ageSeconds, stale and pending before drawing conclusions. Set refresh to true for a forced GitHub collection. A cold range also collects automatically and can take time. The report includes pass rate, CI history errors, conclusion counts, default-branch/PR health, workflow failure signals, elapsed timing statistics in milliseconds and slow-run IDs. Diagnostic IDs link to https://github.com/OWNER/REPO/actions/runs/ID or /actions/workflows/ID. Unavailable/partial data stays explicitly unavailable; it is never converted to a passing result. Cancelled/skipped are excluded from pass rates; timing statistics use successful runs only (timing.basis = success). Timing caveats are the same as in the UI.

Pass `view` for one job-level slice from the local store: `signals`, `stall` (pool queues plus `poolTimings`), `pools`, `losses`, `failures`, `reruns`. `pools` returns `poolTimings` (per runner pool: `jobs` and p50/p90 `queueWaitMs` and `durationMs`) and `poolTimingsByEvent`. Failure and rerun rows carry the run `event` (`pull_request`, `push`, `merge_group`). For merge queue runs, failure rows add `queuePullRequest` (PR number from the queue branch) and `queueOnly` (true: the same job passed in the newest completed pull_request run of that PR, so it fails only in the queue). `failureCountsByEvent` splits `failureCounts` by event.

The read-only `ci` RPC is discoverable via `bb plugin rpc inspect delivery-dashboard ci`. It accepts the same JSON input and can be called by other plugins or agents with `bb plugin rpc call delivery-dashboard ci --input-file query.json --json`. No custom CLI is required. This interface does not dispatch deployments or expose authorization tokens, settings, raw commit history or unused API payloads. Existing UI RPC methods remain private to discovery.

New native tools become available when BB next constructs the provider session; an existing agent can use the CLI/RPC immediately after reload.

## Observer threads

CI events can be pushed to BB threads so an agent watching CI is told instead of polling. Each message is one short plain-text line starting with `[CI Dashboard]`, with ids and a GitHub link, sent with `threads.send` in `auto` mode (an idle agent wakes up). Green runs never produce messages.

What is sent (each type has its own on/off setting, all on by default):

- Merge queue removal (`observeQueueRemoval`): `PR #N removed from merge queue · run <id> attempt <a> · <job>: <class>[ <signature label>], … · failed tests: <up to 5, then +K>` + run link. Classes are the classifier's (`real`, `flake` with the known-flake label, `runner_loss`, `consequence`, …). Failed test names exist only when `flakeArtifacts` names a test-report artifact (Go test2json, Jest/Vitest JSON, JUnit XML) and come from FAILED entries only.
- Removals are confirmed against the PR's merge-queue timeline (GitHub `REMOVED_FROM_MERGE_QUEUE_EVENT` after the group started, retried for 15 minutes, a failed lookup falls back to sending), and only groups with an own failure that the queue did not invalidate by cancelling or replacing them are announced.
- Runner loss on a merge queue or default-branch push run (`observeRunnerLoss`): `Runner lost · <job> · runner <name> · run <id> · <N>[/limit] losses on head <sha7>` + job link. The limit appears when `runnerLossLimit` is above 0. A merge queue loss is not a separate line: it is folded into the removal as `<job>: runner_loss (<N>[/limit] on this head)`, and appears as this line only when the PR stayed in the queue (its removal was never confirmed within 15 minutes); default-branch push losses always use this line.
- Default-branch workflow red (`observeDefaultRed`): `<workflow> red on <branch> · run <id> · jobs: <class counts> · Code looks broken: yes | no | no (red on flakes only) | unknown` + run link. The verdict is the one Investigate prompts use.
- Pool stall (`observePoolStall`, threshold `stallMinutes`), mass cancel (`observeMassCancel`), deployment finished (`observeDeployments`: `Deploy <environment> <success|failure|error> · <sha7> · deployment <id>` + log link).

Never included: log text, annotations, signature match text, env values. Only labels, ids, names and links.

Noise control: every event has a key (`queue:<run>:<attempt>`, `loss:<jobId>`, `red:<run>:<attempt>`, the signal id for stalls and mass cancels, `deploy:<id>:<state>`). Sent keys are persisted in plugin kv (`observer:<repo>`) and kept for the job-history window plus a day, so a restart or reload never repeats an event. A key that can reopen (a pool stall) is repeated only after `observerQuietMinutes` (default 30; 0 repeats at once). `observerBatchMinutes` above 0 collects events into one digest, one line each, sent once the oldest has waited that long. Nothing before a subscription is replayed: a thread only receives events that happened after it subscribed, and an event type switched on later (or off and on again) starts from that moment.

Latency: the live poll (every 60 s) notices a run that is no longer queued or in progress, fetches it (1 request) and, if it ended unsuccessfully, stores its jobs ahead of the history backlog and re-runs the analysis in the same loop, so a queue removal or runner loss reaches the observer within about a minute of the job's completion. A run that starts and ends between two polls is picked up by the periodic history refresh instead.

How to set the observer: Settings → CI Dashboard → `observerThreads` (comma-separated `thr_…` ids; blank turns the feature off), or the agent tool **ci_dashboard_observe**:

```json
{"action":"subscribe"}
```

`subscribe` adds the calling thread (or `threadId`), `unsubscribe` removes it, `list` shows the current observers, and `replace` makes the thread the only observer. Take-over flow for a new manager session: call `replace` with no `threadId`; the previous manager stops receiving events at once and the new thread gets a one-line confirmation (`[CI Dashboard] Subscribed to CI events for <repos>: <types>; quiet window <m> min`). Call `subscribe` when you start watching CI and `unsubscribe` when you stop. The thread must exist and not be archived. Archived or deleted threads, and threads whose messages fail with 404, are removed from the list automatically. Other send failures are logged once per thread and not retried. A change to `observerThreads` (from the tool or the settings UI) takes effect immediately for new subscribers and from the next loop for events.

## Rename compatibility

The visible name, navigation label, documentation, skill and repository directory are CI Dashboard / ci-dashboard. The package name bb-plugin-delivery-dashboard and internal plugin ID delivery-dashboard intentionally stay stable because BB namespaces settings, secrets and SQLite data by that ID. Existing routes under /plugins/delivery-dashboard/dashboard and old collection installs continue to work. New installs use --plugin ci-dashboard; updates continue to use bb plugin update delivery-dashboard. The delivery-dashboard collection entry is a compatibility alias pointing to the same renamed package, not a second installed plugin.


When the history charts are side by side, each header has an Expand button. Expansion simultaneously animates both grid columns and their gap over 300 ms: one card grows to the full row while the other shrinks and fades out. Restore reverses the same transition. Both charts stay mounted so scroll positions and data survive; collapsed content is inert and hidden from assistive technology. The minimum inner width prevents text wrapping from inflating height during collapse. Expansion is independent per repository and survives in-place refreshes and date changes while the component remains mounted. Reduced-motion preferences disable transitions. On narrow layouts charts normally stack and the Expand controls are hidden; an already-expanded chart keeps its Restore control if the pane is narrowed.


Timing aggregates from older versions are detected by their missing success basis and rebuilt locally from retained raw history, including exact cached ranges. Raw history and HTTP pages are preserved, and rebuilding does not advance the actual collection timestamp. If no raw coverage is available, normal collection is needed instead of returning the obsolete aggregate. CI outcome counts, failure signals and the pass-rate formula are unchanged.

Refresh progress preserves cached values, CI diagnostics and charts for fields still pending; only settled fields replace displayed data. Skeletons appear only when that field has no available value. Last checked retains the previous collection timestamp while progress is incomplete.

Confirmed draft deferrals are excluded from pass rates, chart denominators, failure counts and alerts, and shown as Deferred: draft. Only failed pull_request runs of the configured workflow are inspected: the sole unsuccessful job must be the configured job, whose sole unsuccessful step is the configured step. Full paginated jobs from the specific run attempt provide evidence; current PR draft state is never used. Failed or incomplete evidence stays counted as failure with an unverified-candidate notice. Classification is retained with the raw run and reused only for the same attempt and update timestamp; job responses are slimmed and use the existing cache and four-request budget. Local-only snapshots never fetch jobs; the next background refresh completes classification. Older snapshots are rebuilt locally. This adds job requests only for previously unclassified failed CI pull-request runs.

Draft recognition is configurable in Settings → Plugins → CI Dashboard: Draft deferral: workflow name (`draftWorkflow`), only failed job name (`draftJob`) and only failed step name (`draftStep`). All three default to blank, and the rule is disabled unless all three are set. Names are exact, case-sensitive matches, trimmed and limited to 200 characters. Updating them applies to dashboard summaries, charts, interval statistics, failure lists and agent reports. Settings changes invalidate previous cached results and classifications, so matching evidence is collected again. The BB repository import switch appears before the additional repository list.

The three draft-recognition fields are grouped behind a Draft deferral disclosure, collapsed by default. The expanded group has a rounded border, inset rows and horizontal separators; it is visually separated from the remaining settings. A cleanup-safe content script decorates the host settings form; native inputs, validation and autosave are retained. Reopening the settings page collapses the group again. If the host form structure changes, fields remain visible rather than becoming inaccessible.
