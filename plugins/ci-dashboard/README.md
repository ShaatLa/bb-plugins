# CI Dashboard for BB

Adds a responsive **CI Dashboard** page in BB's sidebar with GitHub deployment frequency, open PR count, and CI pass rate for multiple repositories. Refreshes every five minutes by default, with an immediate Refresh icon button. The same reload icon spins while loading, keeping its size and respecting reduced-motion preferences. External links use compact icons.

Open **CI Dashboard** using the pipeline icon in BB’s navigation sidebar. The page route is `/plugins/delivery-dashboard/dashboard`; the old homepage section is removed.

## Setup

Install from the collection:

```sh
bb plugin install git:https://github.com/ShaatLa/bb-plugins.git@main --plugin ci-dashboard
```

For local development:

```sh
npm ci --include=dev
npm run build
bb plugin install . --yes
```

GitHub repositories are discovered automatically from BB projects' `gitRemoteUrl` fields on each refresh. HTTPS, SSH, SCP-style (`git@github.com:owner/repo.git`), and Git URLs are supported. Other Git hosts and projects without a recorded remote are skipped. Each repository has summary cards, green history charts, CI outcome counts, a review queue, the latest production deployment, and a repository activity block for the selected range.

Open **Settings → Plugins → CI Dashboard** to adjust:

- **Additional GitHub repositories** (`repository`): comma-, whitespace-, or newline-separated `owner/repo` entries. Existing single-repository settings continue to work. Automatic and manual entries are de-duplicated case-insensitively.
- **Include GitHub repositories from BB projects** (`importBbRepositories`): enabled by default; disable to track only the manual list.
- **GitHub token override** (`token`): optional secret override. When blank, the backend checks `GH_TOKEN`, then `GITHUB_TOKEN`, then the active GitHub.com account from [`gh auth token`](https://cli.github.com/manual/gh_auth_token), matching BB's GitHub CLI authorization. The CLI must be installed and authenticated on the **BB server machine**. If no credential is available, public repositories use anonymous access with GitHub's lower rate limit. No token is returned to the browser, logged, or copied into plugin settings.
- **Refresh interval** (`refreshSeconds`): integer 30–3600, default 300. Changes apply without reload.

Private repositories require read access to Actions, Deployments, Pull requests, and Contents (for commit statistics). Existing system credentials keep their current permissions; the plugin does not request more scopes. A BB discovery failure is displayed while manual repositories remain available; use Refresh to retry discovery.

## Date range

Use **Date range** to select 1 day, 3 days, 1 week, 2 weeks, 1 month (30 days), or 3 months (90 days). The default is one week. The 1-day preset means today from 00:00 UTC through refresh time; other presets are rolling periods ending at refresh time. **Custom dates** exposes From/Through date pickers and an Apply dates button; both calendar dates are included in UTC, with today's endpoint capped at refresh time. Invalid, reversed, future dates and dates before the UTC calendar date one year ago are rejected (February 29 maps to February 28 in a non-leap year).

The filter applies to deployment frequency, created PRs, commits and changed lines, CI pass rate/outcomes, and both charts across all repositories. Open PRs, the review queue, and the latest production deployment show current state independently of the selected range. Each section uses the BB project name (or a readable repository name for manual entries), with a compact UTC date range and exact timestamps on hover. Switching ranges keeps the previous results and their captions visible until the replacement arrives; superseded responses are ignored. The selection survives sidebar navigation within the app window.

Click any bar in either chart (or focus it and press Enter/Space) to open **Interval statistics** for that repository. The popup shows compact UTC dates with exact interval endpoints on hover, deployment count, created PRs, default-branch commits and added/deleted lines, CI pass rate, and CI outcomes. It loads on demand without clearing the dashboard. Empty bars are also clickable. Future intervals are disabled. Bars may represent four hours for today, an hour for a custom day, a rolling day, or multiple days, depending on the selected range; the popup always uses the actual bar interval, excluding shared boundaries from the earlier bar. The popup stays within the dashboard pane intersected with the visible viewport, including when a native browser pane is open beside it or the split is resized; it also follows zoom, panning, and on-screen keyboard changes; narrow cards stack and long content scrolls vertically. Close with Close, Escape, or a backdrop click. Failed popup requests can be retried; unavailable metrics retain their own explanations.

## Metric definitions

| Metric | Definition |
| --- | --- |
| Deploy frequency | Number of GitHub deployment records created in the selected range divided by its duration in days. Includes all environments and outcomes, so deployment attempts are counted, not just successful production deploys. |
| PRs created | All PRs opened within the selected range, including drafts and PRs that are now closed or merged. Independent of the current open-PR count. |
| Commits | Unique commits in the default branch's reachable history, filtered by committed date within the same selected window. The default-branch name is displayed. |
| Lines added / deleted | Sum of GitHub's per-commit additions/deletions for that commit dataset, across all files (including documentation and generated files). Includes merge commits as reported by GitHub. These are cumulative changed lines, not net repository growth or a count of current source-code lines. |
| Open pull requests | GitHub Search's current open PR count, including drafts. Incomplete search results produce an error. |
| CI pass rate | Successful / completed GitHub Actions workflow runs excluding cancelled and skipped created in the selected range × 100. Includes every branch and workflow; neutral completed runs remain in the denominator. Cancelled and skipped runs are excluded from the pass rate and chart but remain visible in CI outcomes. No remaining completed runs displays “—”. |
| CI outcomes | Counts by conclusion from the same completed-run dataset as the chart and pass rate: passed, failed, cancelled, skipped, and any other reported conclusions such as timed out. “Failed” is the GitHub failure conclusion; timeouts are shown separately. |
| PRs awaiting review | Non-draft open PRs matching GitHub's `review:none` filter, meaning no review has been submitted yet. Shows the total and the five oldest, with links. Age is since PR creation, not time since a review request. |
| Latest production deployment | The newest deployment flagged `production_environment: true` or whose environment is named `production` (case-insensitive). Shows the latest status, environment/ref, creation age, status-update time, and an HTTPS log link, falling back to the repository's deployments page. No status is shown as “unknown”. |

[GitHub deployments API](https://docs.github.com/en/rest/deployments/deployments), [search API](https://docs.github.com/en/rest/search/search), and [workflow runs API](https://docs.github.com/en/rest/actions/workflow-runs) supply the data. For complete histories, CI pass rate, daily series, and outcomes are computed from one dataset, avoiding races with a separate success-count query. Duplicate run IDs are de-duplicated. If counts change during pagination, incomplete histories are hidden and retried on the next refresh; the summary falls back to GitHub count queries.

Opening the dashboard first reads a local server snapshot, then updates from GitHub in the background. The default weekly snapshot is also collected by a background service while the dashboard is closed, using the configured refresh interval. Snapshots survive BB/plugin restarts in plugin-owned SQLite; the eight most recently used ranges are retained. No credentials are stored in snapshot data. Changing settings invalidates snapshots, and refreshes started under older settings cannot replace them. Concurrent refreshes of the same range share one GitHub collection.

The display budget of 600 ms applies to an existing local snapshot. The first collection after installation, a settings change, or selection of an uncached range still requires GitHub; it shows an explicit loading state rather than invented values. Last checked shows the snapshot's actual collection time. Refresh requests fresh data without hiding current cards or charts. Frontend polling runs only while mounted and cleans up on unmount; sidebar remounts additionally reuse the current window's in-memory snapshot. No repository data is stored in browser storage. Requests abort on plugin unload and have a 20-second timeout per API request. Failed RPC refreshes preserve displayed values with a stale-data warning. Deployment pagination continues until the selected window is complete, without a 1,000-record cap. GitHub.com is the supported host.

Each repository also has deployment-throughput and CI-pass-rate bar charts with six four-hour buckets for today (00:00, 04:00, 08:00, 12:00, 16:00, 20:00 UTC), hourly buckets for custom single-day ranges, 12-hour buckets (00:00 and 12:00 UTC) for the three-day preset, UTC calendar-day buckets up to two weeks, and larger whole-day buckets (about 14) for longer ranges. Bars are labelled with their start. Today’s future intervals show “—” and cannot be opened; the current interval ends at refresh time. Deployment frequency for today is the deployment count since midnight. The first and last buckets of a preset may be partial; hover descriptions give their actual boundaries. Dates and hover descriptions use UTC. Zero deployment counts stay zero; days with no completed CI runs show “—”. CI history splits searches above GitHub’s 1,000-run limit into disjoint UTC intervals, then paginates each interval. Pass rate, charts and outcomes use the complete combined dataset, ignoring truncated large-search counts (including GitHub’s 2,500 cap). Failed or inconsistent pagination is unavailable; fallback count summaries are limited to searches of at most 1,000 runs. More than 1,000 runs created in the same second cannot be split further and are unavailable. Production discovery scans newest deployments until a production record is found or the list ends, independently of the selected metric window. Deployment-list requests shared by frequency and production discovery are reused within the refresh.

Commit and line statistics use the [GitHub GraphQL Commit API](https://docs.github.com/en/graphql/reference/commits), which requires authorization even for public repositories. With no system/override token, PR activity can still load and commit/line values show “—” with an explanation. The first page captures the default branch's head commit; remaining pages query that immutable head. All selected commits are read with de-duplication, cursor-cycle protection and completeness checks. Malformed, partial, or failed responses produce unavailable commit/line values instead of partial sums. An empty repository or a genuinely empty seven-day history gives zero.

## Development

```sh
npm test
npm run typecheck
npm run build
```

The backend defines validated settings and schema-checked RPC. The frontend uses BB's sidebar nav panel slot and theme tokens with vendored Button and Card components. Tests cover calculations, pagination, missing data, API errors, settings/RPC validation, system authorization precedence, repository import and de-duplication, secret handling, multiple repository rendering, outcome counts, review queues and ages, production status/link validation, interval refresh, stale values, timer cleanup, preset/custom date validation, UTC endpoints, backend query ranges, and out-of-order filter responses through BB's official testing APIs.

Review filtering follows [GitHub review search qualifiers](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests#search-by-pull-request-review-status-and-reviewer); production status data follows the [deployment statuses API](https://docs.github.com/en/rest/deployments/statuses).

CI history first determines whether a search needs splitting, then fetches each leaf search’s remaining pages concurrently (at most nine more). A shared four-request budget covers all repositories, interval requests and background refreshes. Per-request deadlines start after queueing. Counts, unique run IDs, UTC boundaries and final pagination markers are checked before showing complete history.


The latest-production-deployment card of the configured repository includes **Deploy to production**. The action is configurable and hidden until set: `productionRepository` (owner/repo, blank = disabled), `productionWorkflow` (workflow file name, required with a repository) and `productionRef` (branch or tag, default `main`). Confirming starts that workflow on that ref, preserving the workflow's own checks and GitHub approvals. The target comes only from settings; arbitrary repositories, refs, and workflow paths cannot be supplied. The backend refuses unless both repository and workflow are set and the repository is still one of the configured/imported dashboard repositories, and it blocks overlapping dispatch requests. The existing GitHub authorization must have [Actions write permission](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event). Success means the workflow was requested, not that production has deployed; use View workflow to follow it. Requests are never retried automatically; after an unconfirmed request, check GitHub before trying again.

Repository headings link directly to their GitHub repository using BB’s standard URL opener (the right Browser pane when the built-in browser is selected). Normal link modifiers and copy-link behavior remain available. The dashboard uses a pipeline icon in the sidebar and plugin branding.

The window retains eight range snapshots keyed by configuration and selection. Returning to a loaded range renders its cards immediately while metrics refresh in the background. Completed superseded requests still populate their own cache entry, without replacing the current view; settings changes invalidate pending cache writes. Persisted snapshots only seed ranges absent from memory, so polling cannot reapply older server data.

Complete deployment, CI and commit records are stored with their source snapshot in plugin-owned SQLite. An uncached preset or custom range contained in a stored history is computed locally, anchored to the source snapshot’s endpoint and last-checked time. The local snapshot returns immediately with the created-PR count marked pending; the regular metrics request fills that count separately. Current open PRs, reviews and production reuse the source snapshot. Ranges outside stored coverage require a first GitHub collection; existing aggregate-only snapshots need one refresh to acquire raw history.

Fresh range snapshots are reused until refreshSeconds expires; changing dates does not start another full collection while the cached data is fresh. The Refresh button explicitly forces collection, and expired data refreshes in the background.


Side cards use their content height. Expand **Latest failed runs** in CI health for up to five workflow runs with the failure conclusion, created in the displayed range, with workflow/title, creation time and GitHub run links. Expand **Recent production deployments** for the five latest deployments in the latest production deployment’s environment, with status, ref, SHA and creation time. Compare links use adjacent immutable deployment SHAs and are omitted for identical SHAs. A failed status lookup is shown as unavailable. These lists load only on expansion, share the four-request GitHub budget and 20-second timeout, and keep their response while that snapshot is displayed; closing/reopening does not fetch again. A changed range or refreshed snapshot resets the lists. Errors offer Retry details. Production history is independent of the selected historical range. Refresh uses an inline SVG reload icon so its shape does not depend on the host icon-name mapping.


Repository history is shared across date selections in SQLite, independently of the eight rendered range snapshots. Overlapping requests extend the stored coverage; routine refreshes retain at most the rolling 90-day span unless an explicitly requested custom range needs older data. Repository history refreshes are coalesced across selections. A fresh contained view reuses that history and only obtains its range-specific PR creation count. Snapshot derivation is fully local and never resolves GitHub authorization or waits for a PR API request; unavailable creation counts are marked pending, not zero. Historical dates remain anchored to the source endpoint and timestamp.

Refreshes publish ready repository cards on the metrics-progress channel before the full request settles. The page accepts only its selected range, rejects older request generations, and displays pending fields explicitly. A slow commit history or another repository does not delay ready CI, deployments, PRs or reviews. A failed refresh still preserves the available view.

A shared persistent response cache revalidates GET pages with ETag/If-None-Match, retaining the body and pagination on 304; unsupported endpoints fall back to normal GET. Metadata (PR counts, review queue and deployment statuses) has a separate refreshSeconds lifetime shared across date selections. Manual Refresh bypasses that lifetime and revalidates. Cache keys contain a token hash, never the token, and settings changes clear both histories and HTTP responses and reject old in-flight writes. Up to 512 HTTP pages are retained; cached payloads store only the fields used by metrics, excluding unused deployment payloads and unsafe log links.

Large CI collections use stable UTC week windows, running independent windows and the first split’s siblings concurrently. Deeper splits are sequential to prevent exponential speculative work when GitHub reports inconsistent counts. The active tail is read after closed windows so its pages do not queue behind historical work; a pagination count change retries only that window once before reporting incomplete data. All paths retain the shared four-request limit, per-request deadline, complete leaf count checks, duplicate-ID checks and disjoint boundaries. Old CI pages are revalidated too, so reruns that change an old conclusion are not silently frozen in cache. Unchanged pages need no response-body download.

Commit history always checks the current default-branch head and total count. An unchanged head reuses complete matching cached records. A fast-forward can merge new records only after encountering the prior head (proving ancestry) and matching the complete expected count. A rewritten branch, changed branch, missing ancestry or incomplete merged count falls back to reading the current immutable-head history. First loads, missing coverage, missing ETags and rewritten Git history can still require full downloads.


Automatic cache maintenance runs at startup, after completed snapshot writes and successful repository discovery, and hourly through the existing background service. Entries unused for seven days are removed. Historical records are limited to the past calendar year, from 00:00 UTC on the anniversary date through now. Older raw deployment, CI and commit records are pruned while newer records and their actual freshness timestamps survive. Snapshots with older aggregate windows and HTTP pages containing older history or querying older date ranges are removed whole, preserving pagination counts and ETag correctness. Current-state metadata such as old pull requests still open is retained. The boundary advances daily; cleanup runs at startup and at least hourly while idle. Last access is tracked separately from the data’s freshness timestamp, so using a cached entry never makes old metrics appear freshly collected. Existing repository histories receive an initial access timestamp on upgrade; existing HTTP pages inherit their previous check time. Valid local snapshot reads keep the corresponding repository history active.

Cache budgets retain at most eight range snapshots and 512 HTTP responses, with a combined 64 MiB budget for serialized cache payloads (SQLite/WAL overhead is additional). Byte eviction removes least-recently-used HTTP pages first, then range snapshots, then repository histories, retaining active history ahead of disposable responses. An entry larger than the whole budget may be evicted; subsequent requests collect it again normally, without treating missing history as zero. Successful, complete project discovery removes histories, snapshots and recognized HTTP pages belonging to repositories no longer configured. Discovery failures do not purge unknown repository membership.

SQLite compaction runs only at startup or the hourly idle maintenance pass, with no metrics/history request in flight: VACUUM is used when free pages occupy at least 8 MiB and 25% of the file; WAL is checkpointed and truncated. Normal request completion only evicts rows. Maintenance failures are logged and retried later without failing metric requests. Cache deletion never modifies repositories or GitHub data.


### CI diagnostics and elapsed timings

CI health lists *problems*: open critical or warning job-level signals and run-level alerts. Run-level alerts flag the latest non-cancelled/non-skipped failed run per workflow on the actual default branch and three or more consecutive failures on any branch (workflow and branch kept separate; PR runs never become default-branch alerts; a later success clears the alert; neutral/unknown results break a streak; failure states are failure, timed_out, startup_failure, action_required and stale). Each problem can be **dismissed** (moves under a collapsed Dismissed section, restorable) or handed to a BB session with **Investigate** (a new session in the BB project linked to the repository, or an existing session picked from that project; busy sessions queue the message). Investigating problems show a link to the session. Handled problems stop counting in the navigation badge. Everything else (outcome counts, failure causes, main/PR success rates that exclude cancelled and skipped runs, runner pools, losses, reruns, resolved incidents, history coverage notes, top failing workflows, the lazy failed-run list) is in one collapsed Details.

The timing summary has a workflow selector: it defaults to the workflow named CI (case-insensitive), or All workflows if absent. Changing it recalculates nothing remotely: it uses the cached per-workflow aggregates. Median, average, P95, total and coverage all follow this selector; the workflow breakdown and longest-run list remain repository-wide. All workflows is a pooled run distribution, not a typical CI duration: frequent short automation can dominate its median. CI run timings prioritizes median, mean and nearest-rank P95 as the three large statistics, with total estimated elapsed time in a secondary text line. The P95 label explains on hover that approximately 95% of measured successful runs finish at or below this duration. The card also shows expandable timing statistics per workflow, and the five longest successful runs with GitHub links. Estimates use run_started_at through updated_at for the current completed run record. Missing or invalid intervals are omitted and measured/total coverage is displayed. Only successful completed runs contribute to all timing statistics and the longest-run list. Cancelled, skipped, failed, timed-out, neutral and unknown conclusions are excluded; counts show measured versus successful runs plus the number excluded. Summed elapsed durations include overlapping workflows; they are not wall-clock delivery time, job compute time or billed runner minutes. Reruns or later record updates may inflate estimates; individual attempt history is not fetched.

Runs of one workflow are never silently mixed across events: a workflow may run a light preflight on `pull_request`, the full check on `merge_group` and something short on `push`, and pooling them would make a daily median move with the day's event mix. When the selected workflow has two or more events, the timing summary gets an Event selector (default: the main event, the slowest per successful run among events with at least a tenth of the workflow's successful runs, i.e. the full check; or All events), and the workflow breakdown lists each event's median and sample size. The Median CI run duration and CI run duration p90 charts get the same Event selector and default to the main event, with the shown event in the note under the title; run-count charts default to All events. Each bar of a sample-based chart shows `n <samples>` under its value, and its tooltip says what the value is a median or p90 of (failed, cancelled and skipped runs are excluded). The agent summary carries the same split as `ciInsights.workflows[].events` (`event`, `total`, `passed`, `timing`).

Diagnostics use metadata already returned by workflow-list requests and derive locally from the same retained raw history on date changes. No per-run or per-job timing requests are added. Existing cached histories remain readable; a refresh acquires missing metadata, with versioned HTTP cache keys preventing legacy slim responses from being retained by a 304. Partial CI histories never produce diagnostics or timing totals.


Dashboard hierarchy: headline success/deployment/PR metrics first, then a full-width CI run timings card with larger timing values and side-by-side expandable workflow/run lists, followed by a unified CI health card. CI health shows the problem list first and one collapsed Details with the rest. CI and deployment history charts follow, then repository activity, then equal-width review and production cards. Secondary cards retain content height; all multi-column layouts stack on narrow screens. Interval dialogs keep the compact CI outcomes card without the dashboard-only diagnostics.


Loading states use theme-aware neutral skeletons shaped like KPI values, timing statistics, CI signals/outcomes, activity numbers, lists and charts. The initial dashboard also shows a structural skeleton; lazy details and interval dialogs follow the same pattern. Each pending field reveals independently. Available values stay visible even when marked pending, zeroes remain values, and failures/unavailable data retain explanatory messages rather than skeletons. Skeletons are decorative, with a named busy status for assistive technology, and disable pulsing when reduced motion is requested.


Expanded timing lists use compact inset rows with aligned duration values. Workflows sort by average duration descending (missing averages last); average is the prominent value, with median, P95, measured-run coverage and cumulative total in secondary metadata. Longest-run links separate workflow, duration, branch and run ID; long branch names truncate visually with their full name in the tooltip and accessible link label.


## Agent access

Use the native **ci_dashboard_metrics** tool to read CI data. For example:

```json
{"repository":"owner/repo","selection":{"days":7},"refresh":false}
```

Omit repository for all configured dashboard repositories. Selection defaults to seven days and accepts the same presets or inclusive UTC custom dates as the UI, limited to the past year. Cached local snapshots are returned immediately when available, even if stale; inspect source, updatedAt, ageSeconds, stale and pending before drawing conclusions. Set refresh to true for a forced GitHub collection. A cold range also collects automatically and can take time. The report includes pass rate, CI history errors, conclusion counts, default-branch/PR health, workflow failure signals, elapsed timing statistics in milliseconds and slow-run IDs. Diagnostic IDs link to https://github.com/OWNER/REPO/actions/runs/ID or /actions/workflows/ID. Unavailable/partial data stays explicitly unavailable; it is never converted to a passing result. Cancelled/skipped are excluded from pass rates; timing statistics use successful runs only (timing.basis = success). Timing caveats are the same as in the UI.

The read-only `ci` RPC is discoverable via `bb plugin rpc inspect delivery-dashboard ci`. It accepts the same JSON input and can be called by other plugins or agents with `bb plugin rpc call delivery-dashboard ci --input-file query.json --json`. No custom CLI is required. This interface does not dispatch deployments or expose authorization tokens, settings, raw commit history or unused API payloads. Existing UI RPC methods remain private to discovery.

New native tools become available when BB next constructs the provider session; an existing agent can use the CLI/RPC immediately after reload.

## Job-level signals (0.2.0)

A background service (`ci-signals`, every 60 s) polls queued and in-progress runs per repository (ETag requests, so unchanged pages are free), backfills completed-run job history into a local SQLite store (`ci_jobs`, `ci_attempts`) within a request budget, classifies failed jobs (runner loss, timeout, transient, flake, real, refused, consequence, superseded, cancelled) and derives signals: runner pool stall, runner loss, mass cancel, rerun still failing, flake, transient. Signals are deploy-agnostic: they use run and job facts only and never write to GitHub. Failures on steps listed in the `refusalSteps` setting (comma-separated; blank by default) are classified `refused` (an intentional gate refusal, e.g. a stale candidate): not real, not a runner loss, no job signal, and a run-level alert is dropped when its latest attempt has only refused, aggregator or cancelled jobs. The Investigate prompt starts with a Verdict (per-class counts of the problem's non-success jobs and a yes/no/unknown "Code looks broken"), then covers the problem's runs (streak start, commit and PR title), newer runs and whether each failed job has since passed, the latest deployment per environment, per-day rates over the stored window, and a suggested action per class with who acts; the free-text `investigateNotes` setting (blank by default) is appended verbatim under Team notes for a team's own rerun limits or incident links. It is built from memory and the local store only.

- Incidents are tracked per repository in plugin kv (`incidents:<repo>`); one push per opened incident through `push-notifications` (`notifications.send`), only for critical signals and default-branch warnings that started within 30 minutes, so the first backfill cannot flood the phone.
- Settings (do not invalidate cached GitHub data or stored jobs): `stallMinutes` (10), `jobBudgetPerHour` (1500), `jobHistoryDays` (14), `aggregatorJobs` (comma-separated aggregator job names that only fail because another job did; blank by default), `policyJobs` (comma-separated policy job names whose failures are never treated as flakes; blank by default), `flakeSignatures` (known flake signatures, one `<regex> => <label>` per line; case-insensitive JS regex, `#` comments, at most 50 rules and 4000 characters; blank by default: a failed job that would be `real` becomes `flake` when its failure annotations, its full log or a matching run artifact contain a match, and the label is shown as evidence), `flakeArtifacts` (comma-separated artifact name globs such as `test-results-*`, `*` is the only wildcard; blank by default: artifacts are never downloaded; archives over 20 MB are skipped and an artifact hit applies only when the run attempt has exactly one failed job that would otherwise be real), and the four actor display names (defaults: Runner owner / SRE, PR author, Lead, Manager).
- RPC: `signals` (optional `{repository}`), `navigationBadge` (unhandled problems: `{ count, critical }`), `problemAction` (`{repository, id, action: "dismiss"|"restore"}`), `investigate` (`{repository, id, threadId?}`: sends the problem to that session, or spawns one in the linked BB project; returns `{ threadId }`). Handled state lives in kv `handled:<repo>` (at most 200 entries; entries of closed problems are dropped on the next pass). The `signals` RPC returns `problems` (with `handled`) and `projectId` per repository. Realtime channel `signals-changed` fires when open signals or pool queues change.
- Agent tool / `ci` RPC accept `view`: `summary` (default, adds `signals: { open, pools, backfill, problems }`), `signals`, `stall` (live pool queues plus, per runner pool, `jobs` and p50/p90 `queueWaitMs`/`durationMs` as `poolTimings` and, by event, `poolTimingsByEvent`; there is no separate `pools` view), `losses`, `failures`, `reruns`. Failure and rerun rows carry the run `event` (`pull_request`, `push`, `merge_group`); merge_group failures add `queuePullRequest` (parsed from the `gh-readonly-queue/<base>/pr-<N>-<sha>` branch) and `queueOnly` (the same job passed in the newest completed pull_request run of that PR), and `failureCountsByEvent` splits `failureCounts`. Non-summary views read only the local store and are compact: every row carries a ref (breadcrumb) and is cut by size (about 8 KB per view; the cut is counted in `moreProblems`/`moreSignals`/`moreFailures`/`moreReruns`). Failure rows are `{ref: "job:<id>", run: "run:<id>:<attempt>", name, class, event, at, queuePullRequest?, queueOnly?}`; signal rows have a `ref` instead of a url; problem rows add `refs`. Check `backfill.remaining` and `backfill.coveredSince` before concluding something did not happen.
- Drill down by ref: `ci_dashboard_metrics` / `ci` with `ref=<ref>` (view, selection and refresh are ignored) returns `{ref, kind, summary, facts, related[], next?}` of at most about 4 KB, from memory and the local store only (no GitHub requests, no log text, annotations, signature matches or env values). Refs: `job:<id>`, `run:<id>[:<attempt>]`, `queue:<run>:<attempt>` (with the removal confirmation status), `pool:<name>`, `pr:<n>`, `sha:<sha or 7+ hex chars>`, and problem/signal ids (`run:streak:<id>`, `run:main:<id>`, `runner_loss:<jobId>`, `flake:<jobId>`, `pool_stall:<pool>`, `mass_cancel:<time>`, …). Unknown or ambiguous refs return an error that lists the forms. Observer lines end with `inspect <ref>`; the Investigate prompt has a Refs section.
- Run history now keeps `head_sha` and `pull_requests` (numbers); runs stored by older versions are backfilled once the repository history refreshes.

## Observer threads

Configured BB threads receive short, classified CI event messages (one Markdown line each, starting with **CI Dashboard**, with ids and a GitHub link) through `threads.send` in `queue-if-active` mode: a busy agent gets it after its current turn instead of being interrupted, an idle one wakes up. Events: merge queue removal (PR, run, attempt, per-job class with the known-flake label, failed test names from the configured test-report artifacts), runner loss on a merge queue or default-branch push run (with the loss count on that head commit), default-branch workflow red (with the Investigate "Code looks broken" verdict), pool stall, mass cancel and deployment finished. Green runs never produce messages. Messages never contain log text, annotations, signature match text or env values.

- Settings: `observerThreads` (comma-separated `thr_…` BB thread ids, validated; blank = off), `observeQueueRemoval`, `observeRunnerLoss`, `observeDefaultRed`, `observePoolStall`, `observeMassCancel`, `observeDeployments` (all on by default), `observerQuietMinutes` (30, 0–1440: at most one message per repeating event key, e.g. a pool stall, in this window), `observerBatchMinutes` (0 = send each event at once; N = one digest every N minutes, one line per event), `runnerLossLimit` (0 = not shown; above 0 the runner-loss line reads `N/limit losses on head <sha7>`).
- Agents manage the list themselves with the `ci_dashboard_manage` tool (observer actions `subscribe`, `unsubscribe`, `replace`, `list`; `threadId` defaults to the calling thread; the thread must exist and not be archived). It writes the `observerThreads` setting. A new subscriber gets one confirmation line and no history; archived or deleted threads (and threads whose sends fail with 404) are removed automatically.
- Dedupe: every event has a key (`queue:<run>:<attempt>`, `loss:<jobId>`, `red:<run>:<attempt>`, the signal id, `deploy:<id>:<state>`). Sent keys live in kv `observer:<repo>` for the job-history window plus a day, so restarts never repeat an event. A thread only receives events that happened after it subscribed, and an event type that is switched on later starts from that moment (the first start never replays history). Shared subscription state lives in kv `observers`.
- Latency: when a run seen queued or in progress by the live poll is gone from the next poll, one request (`/actions/runs/{id}`) decides whether it failed; a failed run's jobs and annotations are stored ahead of the history backlog and the analysis is recomputed in that same loop (also whenever a signature re-scan rewrites stored jobs), so queue removals and runner losses reach the observer within about a minute. At most one step's share of the budget (`jobBudgetPerHour` / 60) goes to these run lookups per loop.
- Queue removals are confirmed: a merge-group run counts only with an own failure (not an aggregator or cancellations) and when GitHub's merge-queue timeline for the PR (`REMOVED_FROM_MERGE_QUEUE_EVENT`, one GraphQL request per PR, retried for 15 minutes) shows the removal after the group started; a failed lookup falls back to sending. A merge-queue runner loss is folded into that removal line (`<job>: runner_loss (N[/limit] on this head)`) and stands alone only if the PR stayed queued; groups the queue cancelled or replaced produce nothing.
- Request cost: deployments are polled once per loop per repository with ETag (`/deployments?per_page=30`, a 304 when unchanged) plus one `/deployments/{id}/statuses?per_page=1` for each deployment that is not final yet (at most 10 per loop, newest first, only deployments inside the job-history window). Failed-test names cost one artifact listing plus the downloads of matching artifacts (at most 5) per announced merge queue removal, and only with `flakeArtifacts` set. Every one of these requests is charged to the job-backfill budget.

## Claiming problems

When an agent takes a CI problem into work, the CI health status changes without a click on Investigate. Problem ids come from `ci_dashboard_metrics` (`view=signals`, `problems[].id`) and from observer lines (` · problem <id>` at the end of every line about an open problem: pool stall, mass cancel, runner loss and default-branch red when they are problems; merge queue removals and deployments are messages only).

- Tool `ci_dashboard_manage` with the problem actions (`action`, `id` (required), optional `repository` (needed only with several repositories), `threadId`, `ref`): `take` marks the problem investigating by `threadId` (default: the calling thread; it must exist and not be archived; pass the worker's id when you delegate); `fix_pending` needs `ref` (a PR number like `#12`, a tracker key like `FIX-1` or a URL, at most 80 characters) and keeps `threadId` if given; `release` hands the problem back; `dismiss` dismisses it. An unknown or already closed id is an error. It returns the problem's new `handled` state (`state`: `investigating` | `fix_pending` | `dismissed`, plus `threadId`, `ref`, `by`: `agent` | `user`, `at`), which `ci_dashboard_metrics` shows as well.
- The Handled section of the CI health card lists them: "Investigating in <session>", "Fix pending: <ref>" (a URL or `#N`, a PR of the repository, is a link) and dismissed ones. Restore clears any of them.
- A claim closes silently when the problem resolves. It is dropped automatically when its investigating thread is archived or deleted (a `fix_pending` claim outlives its thread), and when it is older than the `claimTimeoutHours` setting (default 24, `0` = never) with the problem still open. Each automatic drop sends observer threads one line: `[CI Dashboard] Claim dropped · <problem title> · problem <id> · <reason>`. Changes made through the tool are not echoed to observers.

## Storage

The plugin keeps only what the UI or the agent tool can still show; the rest is deleted automatically (hourly), and nothing grows without bound.

- Job rows: `skipped` jobs are not stored; rows hold only fields not already in columns. Rows and their attempts are removed after "Days of job history" + 1 day, immediately when a repository is no longer configured, and oldest days first above a hard 64 MB ceiling.
- Cached GitHub pages, snapshots and run history: removed after 7 days without use, outside the 1-year boundary, for unconfigured repositories, and above a 64 MB cap. Run history deeper than 90 days (the largest preset) is trimmed back to 90 days when no older range was requested for 7 days.
- Stored incident state: at most 200 open signals (most severe, newest first) and 50 resolved ones from the last 7 days; state of unconfigured repositories is deleted.
- The log shows one `Storage: total … MB (jobs …, history …, http cache …, snapshots …, free pages …)` line per hour when the total moved by more than 1 MB. The plugin log file itself is managed by BB.

## Rename compatibility

The visible name, navigation label, documentation, skill and repository directory are CI Dashboard / ci-dashboard. The package name bb-plugin-delivery-dashboard and internal plugin ID delivery-dashboard intentionally stay stable because BB namespaces settings, secrets and SQLite data by that ID. Existing routes under /plugins/delivery-dashboard/dashboard and old collection installs continue to work. New installs use --plugin ci-dashboard; updates continue to use bb plugin update delivery-dashboard. The delivery-dashboard collection entry is a compatibility alias pointing to the same renamed package, not a second installed plugin.


When the history charts are side by side, each header has an Expand button. Expansion simultaneously animates both grid columns and their gap over 300 ms: one card grows to the full row while the other shrinks and fades out. Restore reverses the same transition. Both charts stay mounted so scroll positions and data survive; collapsed content is inert and hidden from assistive technology. The minimum inner width prevents text wrapping from inflating height during collapse. Expansion is independent per repository and survives in-place refreshes and date changes while the component remains mounted. Reduced-motion preferences disable transitions. On narrow layouts charts normally stack and the Expand controls are hidden; an already-expanded chart keeps its Restore control if the pane is narrowed.


Timing aggregates from older versions are detected by their missing success basis and rebuilt locally from retained raw history, including exact cached ranges. Raw history and HTTP pages are preserved, and rebuilding does not advance the actual collection timestamp. If no raw coverage is available, normal collection is needed instead of returning the obsolete aggregate. CI outcome counts, failure signals and the pass-rate formula are unchanged.

Refresh progress preserves cached values, CI diagnostics and charts for fields still pending; only settled fields replace displayed data. Skeletons appear only when that field has no available value. Last checked retains the previous collection timestamp while progress is incomplete.

Confirmed draft deferrals are excluded from pass rates, chart denominators, failure counts and alerts, and shown as Deferred: draft. Only failed pull_request runs of the configured workflow are inspected: the sole unsuccessful job must be the configured job, whose sole unsuccessful step is the configured step. Full paginated jobs from the specific run attempt provide evidence; current PR draft state is never used. Failed or incomplete evidence stays counted as failure with an unverified-candidate notice. Classification is retained with the raw run and reused only for the same attempt and update timestamp; job responses are slimmed and use the existing cache and four-request budget. Local-only snapshots never fetch jobs; the next background refresh completes classification. Older snapshots are rebuilt locally. This adds job requests only for previously unclassified failed CI pull-request runs.

Draft recognition is configurable in Settings → Plugins → CI Dashboard: Draft deferral: workflow name (`draftWorkflow`), only failed job name (`draftJob`) and only failed step name (`draftStep`). All three default to blank, and the rule is disabled unless all three are set. Names are exact, case-sensitive matches, trimmed and limited to 200 characters. Updating them applies to dashboard summaries, charts, interval statistics, failure lists and agent reports. Settings changes invalidate previous cached results and classifications, so matching evidence is collected again. The BB repository import switch appears before the additional repository list.

The three draft-recognition fields are grouped behind a Draft deferral disclosure, collapsed by default. The expanded group has a rounded border, inset rows and horizontal separators; it is visually separated from the remaining settings. A cleanup-safe content script decorates the host settings form; native inputs, validation and autosave are retained. Reopening the settings page collapses the group again. If the host form structure changes, fields remain visible rather than becoming inaccessible.
