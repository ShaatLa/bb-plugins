# Sweep

Sweep refreshes a dedicated server-local checkout and runs a repository script on a per-project interval (default ten minutes). Checks stay in the repository. Sweep notifies the project manager about new findings and changes to Waiting. Python scripts run with python3; other scripts must be executable. Git, Python and BB CLI access must be available on the BB server machine. Checkout location is `<plugin-data>/checkouts/<projectId>`; it is disposable and cleaned before every run.

Set **BB CLI absolute path** to the installed `bb` executable if the server PATH does not include it. Sweep adds its directory to the script PATH and sets BB_CLI. Set **Script PATH** to the normal login PATH when tools such as gh are absent from the server environment. HOME and GitHub authentication variables are inherited without modification.

Set the Git remote URL in the bb project's settings. Sweep reads it each time it refreshes the checkout. Settings → Plugins → Sweep lets you pick a project and set its manager, interval, branch, script and arguments. Valid edits are saved automatically for the selected project. Advanced check options hold the timeout and snapshot protocol. Execution environment holds the shared BB executable and one search directory per line. Every project defaults to disabled.

```json
{"proj_example":{"enabled":true,"branch":"main","script":"checks/sweep.py","args":["--root","{manager}"],"manager":"thr_example","intervalMinutes":10,"timeoutSeconds":300,"snapshots":false}}
```

`{manager}` in arguments is resolved on each run. For cross-plugin delivery, resolve the configured thread with RPC `manager` and check availability before sending. For example, pass `{"projectId":"proj_example"}`, inspect `{manager: string|null}`, and handle a null manager or an unavailable Sweep. `bb sweep manager --project proj_example --json` reads the same ID. The thread may be in another project.

`bb sweep status --project <id> --json` shows configuration, the last run, the delivery receipt and any pending report. Times are Unix milliseconds. `tickId` identifies the latest scheduled tick. `deliveredTickId` and `deliveredTo` identify the accepted report and its destination: the manager's thread ID, `agent-hub`, or `answers`. For notice deliveries, `deliveredNoticeId` identifies the card and `fallbackReason` records why the manager route failed. `managerError` records the last attempted manager delivery's error, and `alertError` shows push failures. `nextRun` is null when Sweep is disabled. Schedules run only while BB and Sweep are loaded. Missed intervals coalesce into one tick.

`bb sweep run --project proj_example --dry-run` refreshes the checkout and executes the configured script. Sweep does not deliver reports, acknowledge snapshots or change scheduled status. `--dry-run` is optional and applies only to `run`. The script can still change external state. Use a script that avoids external writes for read-only checks. Keep a prior automation enabled until the manager confirms a successful scheduled Sweep check, for example `exitCode: 0` in `status` after enabling.

Inspect RPC descriptions and schemas with `bb plugin rpc inspect sweep run` or list all methods with `bb plugin rpc list sweep`. RPC `configure` takes `{projectId,config}` and replaces that project's entire configuration. Omitted optional fields revert to defaults. The native `projects` setting replaces the entire project map. Use those interfaces for legacy full replacements. Sweep ignores the legacy `remote` field. RPC `status`, `manager`, and `run` each take `{"projectId":"proj_example"}`. `run` has the same behavior as the CLI manual check.

For single-field access, use `bb sweep config get [<key>] --project <id>` and `bb sweep config set <key> <value> --project <id>`. Every `config set` and `run` must name exactly one project explicitly. Read commands may use the current thread's project. Pass strings as shell arguments and arrays as JSON, for example `bb sweep config set args '["--brief"]' --project proj_example`. The equivalent RPCs are `config.get {projectId,key?}` and `config.set {projectId,key,value}`. With a key, they return that field only. Set `branch` and `script` before enabling, for example `main` and `checks/sweep.py`. Changing `manager` redirects pending reports too. Manage the native global fields `bbCli` and `runtimePath` through `bb plugin config sweep`, for example `bb plugin config sweep set bbCli /opt/bin/bb`. The legacy `environment.write` RPC replaces both of these fields together.

## Script acknowledgement protocol

Without `snapshots`, stdout and stderr plus exit code are sufficient. Exit 0 after a quiet check, exit 1 to report findings (for example `ACTION stale-status EXA-1: needs review`), or exit 2 or higher for a failure. A crash, refresh error or timeout becomes exit 2.

Reports use BB Markdown. Lines starting with `ANSWER`, `ACTION`, `WAIT` or `STATE` are grouped into sections with Work Board links where a task key is available. Other output and failure diagnostics appear as plain text in a code block. If formatting exceeds the notice size limit, Sweep tries the original full report. `pending` and `delivered` in status retain the original script report and tick ID. Thread messages start with `[bb message from plugin:sweep]` and a blank line, followed by the report.

With `snapshots:true`, Sweep adds `--committed-state <path> --candidate-snapshot <path>`. The committed file may not exist initially. The script must print every item requiring acknowledgement and write a complete replacement JSON document to the candidate path, for example `{"seen":["EXA-1"]}`. It must leave the committed file untouched. Both paths are also available as BB_SWEEP_COMMITTED_STATE and BB_SWEEP_CANDIDATE_SNAPSHOT. The script may omit the candidate when nothing needs acknowledgement. Sweep accepts valid JSON candidates on exit 0 or 1 and delivers a changed candidate with full output, even on exit 0. Sweep ignores candidates on failure.

Sweep stores candidate bytes and the full report in one SQLite row before delivery. It retries the pending report before running the next check and promotes the candidate only after the manager accepts the message or the notice plugin confirms durable delivery. Sweep prefers enabled Agent Hub and uses enabled Answers on installations with the legacy plugin. Notice retries use the same tick ID. If no notice plugin is enabled or the selected RPC fails, Sweep keeps the report pending and attempts a push alert. A crash between manager delivery and acknowledgement may duplicate that message. Changing manager redirects pending messages as well as new results. Manual runs never stage or acknowledge candidates.

Sweep compares structured output with the last confirmed report. A new action, new answer, or any addition to or removal from Waiting triggers a notice. Standard summary counts, item order, and elapsed-time counters on actions do not trigger another notice. A changed failure or unstructured exit-1 diagnostic still triggers delivery. Snapshot candidates that change committed state and snapshot-enabled answers without a candidate always require delivery. Quiet runs and unchanged reports send no notice. Consecutive checkout refresh failures double the check interval up to an hour, or the configured interval if it is longer. A successful refresh resets the delay. Pending delivery retries keep the configured interval.

## Stats

For a Work Board `stale-status` shadow pilot, use the read-only `attention.observations` RPC with `{"projectId":"proj_example","since":0,"limit":25}` and pass `nextCursor` to read the next page. Observations record the Work Board tracker and generation, scan bounds, card keys and resolved immutable IDs, gaps, and whether Sweep staged and accepted delivery of the report. Retries update the original report's receipt. Manual runs are excluded. A row with issues is incomplete evidence. Shadow collection leaves the normal notification route and snapshot acknowledgement unchanged. This release collects shadow data and does not acknowledge ownership transfers.

Open **Sweep** from the bb navigation rail. Use the controls above the statistics to pick a project or change its notification session. Selecting a session saves the project's manager field immediately. The statistics cover checks, deliveries, new items and failures for the last 24 hours, 7 days or 30 days. The dashboard updates after scheduled runs and when Sweep project settings change.

`bb sweep stats --project <id> --days <1-30>` (default one day) and the `stats {projectId,days?}` RPC report scheduled ticks, executed checks, confirmed deliveries by channel, new distinct items by kind, repeated item sightings, suppressed reports and failures by stage. The `answers` counter includes notices delivered to either plugin. The `reminderReports` counter preserves historical totals. New items are fingerprints first seen within the requested window. Sweep keeps counters and fingerprints locally for a rolling 30 days. Manual runs do not enter these totals.

## Archived thread worktrees

Scheduled checks also inspect the project's Git checkouts on the BB server machine. Sweep reports self-created registered worktrees inside an archived project thread's storage, excluding BB-managed worktrees. Each affected thread gets one line with paths, allocated size and Git status. Sweep repeats a path only after it has cleared and recurred. The manager verifies clean paths, lists dirty paths separately and requests the owner's approval in Agent Hub. See the Sweep skill for the removal steps.

## Runner handoff with Work Board (0.7.0)

Install Work Board 0.69.0 first, then Sweep 0.7.0. On its first tick per project Sweep asks Work Board for the runner (RPC `checks.claim`) and records the grant as `handoff.granted`; Work Board has no state for those projects, so current runners keep running, and after the grant Sweep no longer depends on Work Board. If Work Board is installed but unreachable at that first claim, the tick is skipped and retried after a minute; if it is not installed, Sweep runs without a grant. A project that was sent to Work Board is marked (`handoff.sent` in `status`): it refuses every run, enable and `seed-state` until the state comes back with `bb work-board checks export-to-sweep`. The `transfer.*` RPCs (`export`, `chunk`, `confirm`, `preflight`, `import`, `commit`, `cancel`) serve those Work Board commands and are not meant to be called by hand; a handoff pulled from Work Board is staged and applied only once Work Board's ownership row names Sweep. `status` also shows `running`, `importing`, `incoming` and `hasState`. Moving state needs Sweep disabled, idle and with nothing pending.
Install: `bb plugin install git:https://github.com/ShaatLa/bb-plugins.git@0.x --plugin sweep --tag-prefix sweep/`.

For migration, configure the project with its branch and script, disable it with `bb sweep config set enabled false --project proj_example`, and wait for any active check to finish. Then call RPC `seed-state` with the original committed JSON contents as a string, for example `{"projectId":"proj_example","snapshot":"{}"}`. If committed state or a pending report already exists, skip the import. Committed bytes are stored in plugin SQLite. The script receives a fresh temporary read-only file on each run.
